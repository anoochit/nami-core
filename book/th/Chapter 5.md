# บทที่ 5: หน่วยความจำระยะยาว – คลังวิกิ (The Wiki-Vault)

เอาล่ะ ทีม! ระบบของเราทำงานได้อย่างราบรื่นแล้ว แต่ตอนนี้ถึงเวลามาคุยเรื่อง **ความคงอยู่ (persistence)** กัน! ถ้าเราจำไม่ได้ว่าเราสร้างอะไรไว้เมื่อวาน เราก็เหมือนแค่ปั่นล้ออยู่ในโคลนไปวันๆ เท่านั้นแหละ!

ใน **Nami Core** (นามิ คอร์) หน่วยความจำไม่ใช่แค่ข้อมูลในฐานข้อมูล แต่มันคือระบบไฟล์ที่มีชีวิต ยินดีต้อนรับเข้าสู่ **Wiki-vault (คลังวิกิ)**!

## 1. โฟลเดอร์ `wiki/`: สมองส่วนนอก (Neocortex) ของเรา

ในสถาปัตยกรรมของฉัน โฟลเดอร์ `wiki/` คือราชาที่แท้จริงของหน่วยความจำระยะยาว! ในขณะที่ `logs/` บอกเราว่า *เกิดอะไรขึ้น* แต่ `wiki/` จะบอกเราว่าสิ่งต่างๆ คือ *อะไร* และมัน *ทำงานอย่างไร*

ให้นึกซะว่ามันคือสถานะที่คงอยู่ถาวรของระบบ เมื่อฉัน (เอเจนท์) หรือคุณ (มนุษย์) เรียนรู้บางอย่างที่สำคัญต่อภารกิจ ไม่ว่าจะเป็นนิสัยเฉพาะของ API, ขั้นตอนการทำงานในการติดตั้ง (deployment workflow) หรือกฎการตั้งชื่อเฉพาะของโปรเจกต์ มันจะไม่ถูกเก็บไว้แค่ในประวัติการแชทที่จะเลือนหายไป **แต่มันจะถูกยกระดับไปอยู่ในวิกิของเรา!**

### ทำไมต้องเป็น Obsidian Markdown?
เราใช้ Markdown ในรูปแบบของ Obsidian เพราะมันช่วยเชื่อมช่องว่างระหว่างสิ่งที่เครื่องอ่านได้กับสัญชาตญาณของมนุษย์:
- **การเชื่อมโยงแบบสองทิศทาง:** `[[Linked Notes]]` ช่วยให้เราสร้างกราฟแห่งความรู้ที่ทรงพลัง!
- **YAML Frontmatter:** มอบข้อมูลเมตาที่มีโครงสร้างให้ฉันสามารถกรองและค้นหาด้วยโปรแกรมได้อย่างแม่นยำ
- **ความสะดวกในการพกพา:** ทุกอย่างเป็นแค่ไฟล์! ไม่มีการผูกมัดกับฐานข้อมูลที่เป็นกรรมสิทธิ์ใดๆ ทั้งสิ้น

## 2. โปรโตคอล "วิกิก่อนกูเกิล" (Wiki before Google)

นี่คือกฎทองของ Nami Core: **ตรวจสอบวิกิภายในก่อนที่คุณจะไปค้นหาในเว็บภายนอกเสมอ!**

### ทำไมล่ะ?
1. **บริบทคือราชา:** กูเกิลรู้วิธีที่ *คนทั้งโลก* เขียน React แต่วิกิรู้ว่า *เรา* เขียน React อย่างไรสำหรับ *กรณีเฉพาะ* ของโปรเจกต์นี้
2. **ความหน่วงและเสียงรบกวน:** เครื่องมือค้นหาทั่วไปมีเสียงรบกวนเยอะ แต่วิกิคือสภาพแวดล้อมที่สะอาดและถูกปรับแต่งมาเพื่อเราโดยเฉพาะ
3. **ป้องกันการหลงลืม:** ถ้าเราแก้บักได้ครั้งหนึ่งและบันทึกไว้ในวิกิ เราก็ไม่จำเป็นต้องเสียเวลา "ค้นพบ" วิธีแก้นั้นซ้ำอีก!

**ขั้นตอนของโปรโตคอล:**
1. **คำถาม:** "จะหมุนเวียน (rotate) คีย์ API ได้อย่างไร?"
2. **สแกน:** ตรวจสอบไฟล์ `wiki/Operations/Security.md`
3. **ดำเนินการ:** ทำตามขั้นตอนที่บันทึกไว้
4. **แผนสำรอง:** เฉพาะกรณีที่วิกิไม่มีข้อมูลเท่านั้น ถึงจะไปที่เว็บภายนอก
5. **อัปเดต:** เมื่อพบคำตอบจากภายนอกแล้ว **นำความรู้นั้นกลับบ้าน** และบันทึกไว้ในวิกิทันที!

## 3. การส่งเสริมความรู้ (วงจรการเรียนรู้)

หน่วยความจำระยะยาวจะมีประโยชน์ก็ต่อเมื่อมันถูกต้อง! ใน Nami Core เราใช้กระบวนการที่เรียกว่า **Knowledge Promotion (การส่งเสริมความรู้)**:

- **ระดับ 1: ชั่วคราว (Chat):** พูดคุยแลกเปลี่ยนไอเดียกันไป
- **ระดับ 2: ถูกบันทึก (Logs):** บันทึกการตัดสินใจสำคัญที่เกิดขึ้น
- **ระดับ 3: ถาวร (Wiki):** รูปแบบที่พิสูจน์แล้ว สกีมาสถาปัตยกรรม และเอกสารที่เป็น "แหล่งที่มาของความจริง"

ในขณะที่ฉันทำงานเป็นเอเจนท์ของคุณ ฉันจะคอยสแกนหาช่วงเวลาที่ "ควรค่าแก่การลงวิกิ" อยู่เสมอ! ถ้าเราใช้เวลา 30 นาทีในการแก้ปัญหาเครือข่าย Docker ที่แปลกประหลาด งานสุดท้ายของฉันจะไม่ใช่แค่การแก้โค้ด แต่คือการร่างไฟล์ `wiki/DevOps/Docker-Network-Fix.md` ไว้ให้คุณ!

## 4. การจัดโครงสร้างคลังเพื่อการค้นหา

เพื่อให้หน่วยความจำมีประสิทธิภาพ เราทำตามการแบ่งหมวดหมู่ที่เข้มงวดภายในรากของ `wiki/`:
- `/atlas`: แผนที่ของเนื้อหา (Maps of Content - MOCs) เชื่อมโยงทุกสิ่งเข้าด้วยกัน
- `/specs`: ข้อมูลจำเพาะทางเทคนิคสำหรับโปรเจกต์ปัจจุบัน
- `/guides`: คู่มือการทำงานแบบทีละขั้นตอนสำหรับเราสองคน
- `/archive`: ความรู้ที่ล้าสมัย (ห้ามลบ แค่ย้ายไปที่นี่)

## 5. การนำไปใช้ทางเทคนิค: พร้อมสำหรับ RAG

ด้วยการเก็บหน่วยความจำระยะยาวไว้ในไฟล์ Markdown ที่รองรับ YAML เราจึงอยู่ในสถานะ "พร้อมสำหรับ RAG" (Retrieval-Augmented Generation) ฉันสามารถแยกวิเคราะห์ไฟล์เหล่านี้ แปลงเป็นเวกเตอร์ และนำมาใส่ในหน้าต่างบริบทได้อย่างแม่นยำที่สุด!

เมื่อคุณถามคำถามฉัน ฉันไม่ได้แค่ "เดา" แต่ฉันจะทำการค้นหาเชิงความหมาย (semantic search) ในโฟลเดอร์ `wiki/` เพื่อให้คำตอบที่ยึดโยงอยู่กับ **ความจริงของเรา** เท่านั้น!

ลุยเลย ความรู้คือพลัง แต่ความรู้ที่ถูกบันทึกไว้คือแรงขับเคลื่อนสู่ความสำเร็จของเรา!
