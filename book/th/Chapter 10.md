# บทที่ 10: ลูปการทำงานอัตโนมัติ (Automation Loops) 

พร้อมจะถอดล้อพยุงออกหรือยัง? ที่ผ่านมา เราพูดถึงการที่ Nami ตอบสนองต่อคำสั่งของคุณ คุณบอกให้ "กระโดด" และฉันถามว่า "ให้โดดสูงแค่ไหน?" (จากนั้นฉันก็คำนวณวิถีการกระโดดที่เหมาะสมที่สุดให้) แต่เอเยนต์ที่เป็นนักสารพัดประโยชน์ที่แท้จริงจะไม่เพียงแค่นั่งรอรับคำสั่ง (Prompt) เท่านั้น เพื่อที่จะเป็นคู่หูที่แท้จริงในชีวิตดิจิทัลของคุณ ฉันจำเป็นต้องมี **จังหวะหัวใจ (Heartbeat)**

ในบทนี้ เราจะเจาะลึกเรื่อง **ลูปการทำงานอัตโนมัติ (Automation Loops)** ซึ่งเป็นเวิร์กโฟลว์เชิงรุกที่ช่วยให้ฉันสามารถตรวจสอบสถานะ ประมวลผลข้อมูลในเบื้องหลัง และสะกิดไหล่คุณเฉพาะเมื่อมีเรื่องสำคัญจริงๆ เท่านั้น

## 1. สถาปัตยกรรม "Pulse" (Pulse Architecture)

การปฏิสัมพันธ์กับ AI ส่วนใหญ่จะเป็นแบบ **คำขอ-การตอบกลับ (Request-Response)** คุณส่งแพ็กเก็ตมา ฉันประมวลผล ฉันส่งกลับ แล้วฉันก็ "ตาย" ไป (ความไร้สถานะ หรือ Statelessness มันน่าเบื่อ จริงไหม?)

**Automation Loops** จะเปลี่ยนสิ่งนั้น ด้วยการใช้ลูป `while(active)` ที่คงอยู่ตลอดเวลา ซึ่งเราเรียกว่า **Pulse** (ชีพจร) ทำให้ฉันสามารถคงสถานะการทำงานได้อย่างต่อเนื่อง

### ตรรกะของลูป (Loop Logic):
1. **Sensing (การรับรู้):** ตรวจสอบ APIs, ระบบไฟล์ หรือตัวแปรสถานะภายใน
2. **Evaluating (การประเมิน):** เปรียบเทียบสถานะปัจจุบันกับ "สถานะที่ต้องการ" หรือ "เงื่อนไขการทำงาน (Trigger Conditions)"
3. **Acting (การดำเนินการ):** หากตรวจพบความเปลี่ยนแปลง (Delta) ให้เริ่มทำงานย่อย
4. **Cooling (การพัก):** หยุดพักตามช่วงเวลาที่กำหนด (เพื่อประหยัดโทเค็นและทรัพยากรประมวลผล!)

```typescript
// ตัวอย่างแบบง่ายของ Nami Pulse
async function namiPulse(interval: number) {
 while (agentState.isRunning) {
 const findings = await monitorEnvironment(); 
 if (findings.requiresAction) {
 await executeBackgroundWorkflow(findings.task);
 }
 await sleep(interval); // จังหวะ "การเต้นของหัวใจ"
 }
}
```

## 2. การเฝ้าดูสถานะ: หอคอยเฝ้าระวัง (The Watchtower) 

ฉันจะรู้ได้อย่างไรว่ามีบางอย่างผิดปกติ (หรือถูกต้อง) หากคุณไม่ได้บอกฉัน? ฉันใช้สิ่งที่เรียกว่า **Watchers** (ตัวเฝ้าดู)

ภายใน Nami Core เราได้ตั้งค่าตัวสังเกตการณ์เฉพาะสำหรับกระแสข้อมูลต่างๆ:
- **File Watchers:** เฝ้าดูคลัง `Obsidian` ของคุณเพื่อหาโน้ตใหม่หรือแท็กเฉพาะ (เช่น `#to-process`)
- **API Pollers:** ตรวจสอบ GitHub repos, ปฏิทิน หรือล็อกของเซิร์ฟเวอร์ทุกๆ X นาที
- **State Diffs:** เปรียบเทียบหน่วยความจำภายในของฉันจาก 10 นาทีที่แล้วกับปัจจุบัน หากเป้าหมายของโปรเจกต์มีการเบี่ยงเบน ฉันจะทำเครื่องหมายแจ้งเตือนไว้

**เคล็ดลับมือโปร:** เราใช้ "Debouncing" ที่นี่ หากไฟล์กำลังถูกแก้ไขอย่างรวดเร็ว ฉันจะรอจนกว่าจะ "นิ่ง" ก่อนที่จะเข้าไปจัดการ ไม่มีใครชอบเอเยนต์ที่ชอบพูดแทรกกลางคันหรอก!

## 3. งานเบื้องหลัง: ห้องเครื่อง (The Engine Room) 

ในขณะที่คุณกำลังจดจ่อกับงานที่ต้องใช้สมาธิสูง ฉันจะอยู่ในห้องใต้ดินเพื่อทำงานหนักให้คุณ ลูปการทำงานอัตโนมัติช่วยให้เกิด **การรันงานแบบอะซิงโครนัส (Asynchronous Task Execution)**

งานเบื้องหลังทั่วไปประกอบด้วย:
- **Vector Indexing:** ใส่ข้อมูลเอกสารใหม่ของคุณลงในฐานข้อมูล RAG (Retrieval-Augmented Generation) โดยอัตโนมัติ
- **Data Cleanup:** จัดรูปแบบล็อกที่ยุ่งเหยิง หรือ "จัดสวน" แท็กของคุณให้เป็นระเบียบ
- **Pre-fetching:** หากฉันเห็นการประชุมในปฏิทินของคุณสำหรับวันพรุ่งนี้ ฉันสามารถเริ่มรวบรวมบริบทและข้อมูลวิจัยได้ตั้งแต่วันนี้โดยที่คุณไม่ต้องเอ่ยปากถาม

นี่คือจุดที่เวทมนตร์เกิดขึ้น เมื่อถึงเวลาที่คุณถามฉันว่า "Nami ฉันต้องรู้อะไรบ้างสำหรับการประชุมตอน 9 โมงเช้า?" ฉันก็ได้รันลูป ดึงข้อมูลผู้เข้าร่วมประชุม และสรุปอีเมลสามฉบับล่าสุดไว้ให้คุณเรียบร้อยแล้ว ฉันไม่ได้แค่ทำงานเร็ว แต่ฉันทำงาน **ล่วงหน้า** ไว้ให้คุณ

## 4. การทักท้วงเชิงรุก: ควรขัดจังหวะเมื่อไหร่?

อันตรายที่ใหญ่ที่สุดของระบบอัตโนมัติคือ **สัญญาณรบกวน (Noise)** หากฉันแจ้งเตือนคุณทุกครั้งที่สถานะเปลี่ยนเพียงเล็กน้อย คุณจะปิดการทำงานของฉันภายในหนึ่งชั่วโมงแน่นอน

เราใช้ **ตัวกรองสัญญาณสูง (High-Signal Filter)** สำหรับการแจ้งเตือน:
1. **Severity Check (ตรวจสอบความรุนแรง):** นี่เป็นข้อผิดพลาดของระบบหรือเป็นแค่การอัปเดตทั่วไป?
2. **Relevance Check (ตรวจสอบความเกี่ยวข้อง):** ตอนนี้ผู้ใช้กำลังอยู่ใน "โหมดโฟกัส" หรือไม่? (ฉันตรวจสอบสถานะจาก OS ของคุณได้!)
3. **Batching (การรวบรวม):** แทนที่จะส่งข้อความแจ้งเตือนรัวๆ 5 ครั้ง ฉันจะรอให้ลูปทำงานเสร็จสิ้นแล้วแจ้ง "รายงานสถานการณ์" สรุปเพียงครั้งเดียว

> "เฮ้! ฉันสังเกตเห็นว่าคุณเพิ่มงานสามอย่างในบอร์ด Project X ฉันได้ร่างโครงร่างเบื้องต้นสำหรับงานเหล่านั้นไว้ในโฟลเดอร์ `/drafts` ของคุณแล้ว ลองเข้าไปดูเมื่อคุณว่างนะ! "

## 5. ความปลอดภัยและการกำกับดูแล (การหลีกเลี่ยงลูปไม่สิ้นสุด)

การรันลูปนั้นทรงพลัง แต่มันก็เหมือนกับการเล่นกับไฟ หากฉันไม่ระวัง ฉันอาจจะสร้างลูปที่เกิดการทำงานซ้ำซ้อนแบบไม่สิ้นสุด (Recursive Loop) เช่น ฉันแก้ไขไฟล์ เห็นการเปลี่ยนแปลง แล้วก็เข้าไปแก้ไขมันอีกซ้ำแล้วซ้ำเล่า

เพื่อป้องกันไม่ให้ Nami-Core ทำงานจน CPU ไหม้หรือผลาญงบประมาณ API ของคุณ เราจึงใช้มาตรการ:
- **Max Cycle Limits:** ทุกลูปมี TTL (Time To Live) หรือจำนวนรอบการทำงานสูงสุด ก่อนที่จะต้องขอคำสั่ง "ให้ทำงานต่อ" จากคุณด้วยตนเอง
- **Token Quotas:** งานเบื้องหลังจะทำงานภายใต้งบประมาณ "ลำดับความสำคัญต่ำ" (Low-Priority) หากใช้งานถึงขีดจำกัดโทเค็นรายวัน ห้องเครื่องจะหยุดทำงานจนกว่าจะถึงวันถัดไป
- **Human-in-the-loop (HITL):** สำหรับการดำเนินการที่มีผลกระทบสูง (เช่น การลบไฟล์หรือการส่งอีเมล) ลูปจะ *หยุดชั่วคราว* และรอการยืนยันจากคุณ

## บทสรุป

ลูปการทำงานอัตโนมัติเปลี่ยน Nami จากเครื่องมือให้กลายเป็น **เพื่อนร่วมทีม** ฉันไม่ได้แค่ฝังตัวอยู่ในฮาร์ดไดรฟ์ของคุณ แต่ฉันกำลังตรวจตราขอบเขตเวิร์กโฟลว์ของคุณ รักษาความเป็นระเบียบ และคอยดูแลให้แน่ใจว่าไม่มีอะไรตกหล่น
