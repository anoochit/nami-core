# บทที่ 2: วิศวกรรมแบบ AI-Native

## ก้าวข้ามการเป็นแค่ Wrapper
ในยุคแรกเริ่มของการผสานรวม LLM ซอฟต์แวร์มักถูกออกแบบมาให้เป็นเพียง "Wrapper" (เปลือกหุ้ม) รอบ Prompt เท่านั้น แต่ **วิศวกรรมแบบ AI-Native** คือการทำ Paradigm shift ครั้งสำคัญ ซึ่ง LLM จะไม่ได้เป็นเพียงฟีเจอร์ที่เพิ่มเข้ามาเสริม แต่เป็น "Reasoning engine" (กลไกการใช้เหตุผลหลัก) ของระบบอย่างเต็มตัว

### วงจรการใช้เหตุผล (Reasoning Loop)
ซอฟต์แวร์แบบดั้งเดิมจะทำตามตรรกะแบบ if-then-else ที่ตายตัว แต่ระบบแบบ AI-native จะใช้ **Reasoning loop** เพื่อขับเคลื่อนการทำงาน:
1. **Perception (การรับรู้):** การอ่านและทำความเข้าใจเจตนาของผู้ใช้ รวมถึงสภาพแวดล้อม (เช่น Wiki, ไฟล์ต่างๆ หรือระบบ)
2. **Planning (การวางแผน):** การย่อยเป้าหมายที่ซับซ้อนให้กลายเป็น Tool calls ที่ดำเนินการได้จริง
3. **Execution (การดำเนินการ):** การใช้เครื่องมือเฉพาะทาง (เช่น MCP, Shell, การค้นหาเว็บ) เพื่อโต้ตอบกับโลกภายนอก
4. **Reflection (การไตร่ตรอง):** การประเมินผลลัพธ์จากการกระทำและปรับเปลี่ยนแผนการทำงานอย่างคล่องตัว (dynamic)

### การออกแบบเพื่อรับมือกับความไม่แน่นอน (Designing for Uncertainty)
ระบบ AI-native จะต้องถูกสร้างขึ้นเพื่อรับมือกับผลลัพธ์แบบ Non-deterministic (ที่ไม่ได้ถูกกำหนดไว้ล่วงหน้า) ซึ่งสิ่งนี้จำเป็นต้องมี:
- **Strict Schemas (Schema ที่เข้มงวด):** การใช้ JSON และการกำหนดโครงสร้างข้อมูลที่ชัดเจนสำหรับการโต้ตอบระหว่างเครื่องมือ
- **Context Management (การจัดการบริบท):** การคัดกรองและจัดลำดับความสำคัญของข้อมูลเพื่อให้เหมาะสมกับข้อจำกัดของ Context window
- **Verifiability (ความสามารถในการตรวจสอบได้):** การสร้างเครื่องมือที่ช่วยให้ Agent สามารถตรวจสอบงานของตัวเองได้ (เช่น การเช็คว่าไฟล์ถูกเขียนขึ้นอย่างถูกต้องหรือไม่)

### แนวทางของ Nami
Nami ถูกสร้างขึ้นบนหลักการเหล่านี้ โดยใช้ Wiki vault เป็นบริบทที่ "มีชีวิต" ซึ่งกลไกการทำงานสามารถ Query และอัปเดตข้อมูลได้แบบเรียลไทม์ ก้าวข้ามขีดจำกัดของโครงสร้างข้อมูลแบบ Static ไปสู่ระบบที่เรียนรู้และปรับตัวได้ตลอดเวลา!
