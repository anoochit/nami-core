# บทที่ 2: วิศวกรรมแบบ AI-Native

## ก้าวข้ามการเป็นแค่เปลือกหุ้ม (Beyond the Wrapper)
ในยุคแรกเริ่มของการผสานรวม LLM ซอฟต์แวร์มักถูกออกแบบมาให้เป็นเพียง "เปลือกหุ้ม" (wrapper) รอบพรอมต์ (prompt) เท่านั้น แต่ **วิศวกรรมแบบ AI-Native** คือการปรับเปลี่ยนกระบวนทัศน์ (paradigm shift) ครั้งสำคัญ ซึ่ง LLM จะไม่ได้เป็นเพียงฟีเจอร์ที่เพิ่มเข้ามาเสริม แต่เป็น "กลไกการใช้เหตุผลหลัก" (central reasoning engine) ของระบบอย่างเต็มตัว

### วงจรการใช้เหตุผล (The Reasoning Loop)
ซอฟต์แวร์แบบดั้งเดิมจะทำตามตรรกะ if-then-else ที่ตายตัว แต่ระบบแบบ AI-native จะใช้ **วงจรการใช้เหตุผล** เพื่อขับเคลื่อนการทำงาน:
1. **การรับรู้ (Perception):** การอ่านและทำความเข้าใจเจตนาของผู้ใช้ รวมถึงสภาพแวดล้อมในขณะนั้น (เช่น Wiki, ไฟล์ต่างๆ, หรือระบบ)
2. **การวางแผน (Planning):** การย่อยเป้าหมายที่ซับซ้อนให้กลายเป็นการเรียกใช้เครื่องมือ (tool calls) ที่สามารถดำเนินการได้จริง
3. **การดำเนินการ (Execution):** การใช้เครื่องมือเฉพาะทาง (เช่น MCP, Shell, การค้นหาเว็บ) เพื่อโต้ตอบกับโลกภายนอก
4. **การไตร่ตรอง (Reflection):** การประเมินผลลัพธ์จากการกระทำและปรับเปลี่ยนแผนการทำงานอย่างคล่องตัว (dynamic)

### การออกแบบเพื่อรับมือกับความไม่แน่นอน (Designing for Uncertainty)
ระบบ AI-native จะต้องถูกสร้างขึ้นเพื่อรับมือกับผลลัพธ์ที่ไม่ได้ถูกกำหนดไว้ล่วงหน้า (non-deterministic outputs) ซึ่งสิ่งนี้จำเป็นต้องมี:
- **Schema ที่เข้มงวด (Strict Schemas):** การใช้ JSON และการกำหนดโครงสร้างข้อมูลที่ชัดเจนสำหรับการโต้ตอบระหว่างเครื่องมือ
- **การจัดการบริบท (Context Management):** การคัดกรองและจัดลำดับความสำคัญของข้อมูลเพื่อให้เหมาะสมกับข้อจำกัดของ context window
- **ความสามารถในการตรวจสอบได้ (Verifiability):** การสร้างเครื่องมือที่ช่วยให้ออโตโนมัสเอเจนต์ (agent) สามารถตรวจสอบงานของตัวเองได้ (เช่น การเช็คว่าไฟล์ถูกเขียนขึ้นอย่างถูกต้องหรือไม่)

### แนวทางของ Nami (Nami's Approach)
Nami ถูกสร้างขึ้นบนหลักการเหล่านี้ โดยใช้ Wiki vault เป็นบริบทที่ "มีชีวิต" ซึ่งกลไกการทำงานสามารถเรียกสอบถาม (query) และอัปเดตข้อมูลได้แบบเรียลไทม์ ก้าวข้ามขีดจำกัดของโครงสร้างข้อมูลแบบคงที่ (static) ไปสู่ระบบที่เรียนรู้และปรับตัวได้ตลอดเวลา!
